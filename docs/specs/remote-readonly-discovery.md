# T02/T12/T13 — ตรวจฐานเดิมแบบอ่านอย่างเดียว

วันที่: 16 พฤศจิกายน 2026 (Asia/Bangkok)

## ขอบเขตที่ได้รับอนุญาต

ผู้ใช้ระบุฐานบัญชี `CENTRAL` และฐานหนังสือ `GenBookno_DB` พร้อมอนุญาตให้อ่านฐานเดิมเท่านั้น และให้นำข้อมูล/ผู้ใช้มาระบบใหม่ การเขียนปลายทางต้องแยกจากฐานเดิม ไม่รวมการเปิดใช้งานจริงหรือเปลี่ยนข้อมูลต้นทาง ห้ามเก็บ credential ที่ได้รับลงเอกสารนี้ source code หรือผลทดสอบ

## สิ่งที่ตรวจได้

- DNS และ TCP/3306 ของปลายทางที่ระบุเข้าถึงได้
- การเชื่อม MySQL โดยบังคับ TLS ทั้งสองเครื่องหยุดด้วย `HANDSHAKE_NO_SSL_SUPPORT` ก่อนอ่าน schema หรือข้อมูล
- ระบบตรวจอนุมัติอัตโนมัติปฏิเสธการเชื่อมแบบไม่เข้ารหัส เนื่องจากสิทธิ์อ่านที่ได้รับยังไม่รับรองความเสี่ยงการส่ง credential/ข้อมูลโดยไม่มี TLS จึงยังไม่ได้ลองต่อแบบนั้น ต้องมีช่องทางเข้ารหัสหรือคำอนุญาตเพิ่มเติมก่อนดำเนินส่วนที่ติดเงื่อนไข
- ยังไม่มีผล query ข้อมูลจริง ไม่มีการ login ด้วยบัญชีบุคลากร ไม่มีการนำเข้าหรือเขียนฐานเดิม/ฐานใหม่ในรอบนี้

## ผลตรวจ static source เดิม

เส้นทาง `application/controllers/user.php` ตรวจ `STAFF_INFO.LOGIN`/`PASSWORD` แบบ parameter binding และ `ACTIVE=1` ไม่พบการ hash รหัสผ่านใน controller นี้ จากนั้น lookup `STAFF_ID` โดยต้องมี `START_DATE` และ reference `PREFIX` รหัสผู้ใช้ที่เก็บใน session คือ `STAFF_ID` และหน่วยงานคือ `DEPT_ID` รายละเอียดนี้เป็นผลจาก source ในเครื่อง ยังไม่ใช่หลักฐาน schema/ข้อมูลของ server ปัจจุบัน

`userlevel` เก็บระดับผู้ใช้, `userbook` เก็บผู้จัดการชุดเลข, `bookdept_user` เก็บสิทธิ์ใช้ชุดเลข ต้องไม่ตีความทั้งสามเป็นสิทธิ์เดียวกัน และต้องไม่ยกระดับสิทธิ์อ่านหนังสือลับหรือแก้แทนจาก numeric role เดิมโดยอัตโนมัติ

การ import ผู้ใช้จะเก็บรหัส/profile ที่จำเป็นและความเชื่อมโยงต้นทาง ไม่คัดลอก `PASSWORD` เข้าฐานใหม่ ต้องตรวจรหัสซ้ำ ผู้พ้นสภาพ เจ้าของประวัติที่ไม่มีบัญชี และหน่วยงาน ณ วันออกแยกจากหน่วยงานปัจจุบัน ห้ามจับคู่ด้วยชื่อหรือ email แทนรหัสที่ยังไม่พิสูจน์

## งานที่ต้องทำหลังเชื่อมได้

1. อ่าน schema/charset/collation/engine และคีย์ของตารางที่จำเป็นใน read-only transaction ไม่ใช้ DDL/DML หรือ table locks ที่ต้นทาง
2. อ่าน snapshot หนังสือและตารางสิทธิ์ พร้อม profile เฉพาะบุคลากรที่เกี่ยวข้อง โดยไม่ SELECT ค่า `PASSWORD`; ตรวจว่าตาราง transactional หรือไม่ก่อนอ้าง consistent snapshot
3. ตรวจ exact-ID mapping, orphan, duplicate, สถานะ, เรื่องว่าง และยอดรายชุด/ปี; เก็บต้นฉบับและกันเลขตาม ADR 0001
4. เตรียมฐานใหม่แบบคงข้อมูลข้าม restart แยกจาก `dev:local` ที่ล้างข้อมูลทุกครั้ง ปิด issuance gate ระหว่างนำเข้าและตรวจ replay/rollback/สิทธิ์อ่าน
5. เชื่อมการตรวจบัญชีจริงกับ session ที่เพิกถอนได้ ทดสอบบัญชีที่ได้รับอนุญาตและ failure cases ก่อนตรวจรับ T13; รหัสบริการ DB ไม่ใช่บัญชีบุคลากรที่ใช้พิสูจน์ login สำเร็จ

เกณฑ์ยังคง T02 4/5, T12 3/6, T13 0/6 ไม่ถือว่าการให้ข้อมูลเชื่อมต่อหรือการเข้าถึง TCP เป็นการตรวจรับงาน

## เครื่องมือและผลตรวจในเครื่อง

เพิ่ม `tools/migration/remote-source.mjs` เป็นตัวเชื่อมอ่านอย่างเดียวที่จำกัดปลายทางตามที่ได้รับอนุญาต ใช้ TLS พร้อมตรวจ certificate/hostname เป็นค่าเริ่มต้น ไม่มี fallback อัตโนมัติ และเปิด `START TRANSACTION READ ONLY` ก่อน query เครื่องมือให้เรียกได้เฉพาะ SELECT/SHOW ในรูปแบบที่จำกัด ปฏิเสธ DML/DDL, หลาย statement, comments, row locks, การเขียน/อ่านไฟล์ และ function ที่ไม่ได้อนุญาต พร้อม rollback/ปิด connection เมื่อจบและปิดบังรายละเอียด error

คำสั่งที่มีค่าพารามิเตอร์ต้องใช้ `execute()` เพื่อ bind ที่ server; `query()` รับเฉพาะ SQL คงที่โดยไม่มีค่าพารามิเตอร์ เพื่อไม่พึ่งการ escape ข้อความกับ `sql_mode` ของฐานเดิมที่ยังไม่ทราบ

ตัวเลือกไม่ใช้ TLS ต้องเลือกโดยชัดแจ้ง ตรวจว่า DNS ทุก address เป็น RFC1918 และตรึง address ที่ตรวจแล้ว การมีตัวเลือกนี้ไม่ใช่คำอนุญาตให้เชื่อมจริง รอบนี้ไม่ได้เรียกใช้หลังระบบตรวจอนุมัติปฏิเสธ

ผลตรวจ 16 พฤศจิกายน 2026: `node --test tools/migration/remote-source.test.mjs` ผ่าน **6/6** ด้วย connection/DNS จำลองทั้งหมด รวมการปฏิเสธ SQL ที่มีผลข้างเคียง การไม่ retry แบบไม่เข้ารหัส การปิด connection และ error redaction; `npm run lint` และ `npm run typecheck` ผ่าน ผลเหล่านี้ตรวจเครื่องมือในเครื่อง ไม่ใช่ผล query schema, import หรือ login จริง
