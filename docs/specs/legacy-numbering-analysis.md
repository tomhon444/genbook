## ข้อควรแก้ในระบบใหม่

- โค้ดเดิมใช้เลขสูงสุดบวกหนึ่ง จึงไม่ใช่กลไกรับประกันเลขไม่ซ้ำเมื่อขอพร้อมกัน ระบบใหม่ต้องจัดสรรอย่าง atomic พร้อม unique constraint ตามขอบเขตที่เจ้าของยืนยัน
- การตรวจช่วงเวลา/วันหยุดตอนเปิดฟอร์มไม่ได้รับประกันว่าคำขอที่มาถึงตอนบันทึกยังอยู่ในเงื่อนไข `save()` เรียก model โดยไม่ตรวจเงื่อนไขเวลาเดิมซ้ำ ต้องยืนยันว่าจะใช้เวลารับคำขอหรือเวลาจัดสรร แล้วบังคับฝั่ง server ตอนดำเนินการ
- ยังไม่พบการตั้ง timezone ชัดเจนจากการค้น `date_default_timezone_set` ใน application และ index; ไม่ได้ตรวจ runtime/php.ini จึงยังสรุป timezone ของเครื่องเดิมไม่ได้ ระบบใหม่ยึด Asia/Bangkok ตามสเปกที่ยืนยันแล้ว
- การมี dump และบันทึกย้าย runtime ภายในเครื่อง ไม่ใช่คำอนุมัติย้ายข้อมูลไปยังระบบใหม่ ไม่ใช้ `MAX+1` ของ snapshot เป็นเลขเปิดระบบจริง
- model รับ `user_request` จาก POST และใช้ session เมื่อค่าว่าง จึงไม่ถือเป็นหลักฐานว่าอนุญาตให้ขอแทนบุคคลอื่นโดยถูกต้อง ต้องตรวจสิทธิ์ฝั่ง server ตามตารางสิทธิ์ใหม่ ([genbook_model.php](C:/laragon/www/book-number/application/models/genbook/genbook_model.php:280))

## ผลการตรวจและข้อจำกัด

- ไล่เส้นทาง controller → model → formatter และตรวจโครงสร้าง/aggregate ของ SQL เต็มโดย agent คนละส่วน ไม่ execute โค้ดเก่าหรือ SQL
- ไม่ทดสอบ login, runtime, concurrency, rollback หรือสิทธิ์จริง และไม่ถือว่าการวิเคราะห์นี้ผ่านเกณฑ์ยืนยันของเจ้าของระบบ
- กติกาเลขไม่ซ้ำของระบบใหม่ยังต้องทดสอบกับ implementation ใหม่หลังยืนยัน scope; รายงานนี้พบข้อจำกัดของระบบเดิม ไม่ได้แก้ข้อจำกัดนั้น
- QA ตรวจเทียบ source และลิงก์ 50 จุดในรอบก่อนเพิ่มส่วน SQL/ตัวอย่างท้ายรายงาน ไม่พบข้อขวางหรือข้อมูลลับ ส่วน SQL/ตัวอย่างที่เพิ่มท้ายยังไม่ได้ตรวจซ้ำครบโดย QA; ตัวเลข SQL อาศัยผลตรวจโดย database agent ไม่อ้างว่า QA คำนวณ aggregate ซ้ำแล้ว งานรอบนี้เปลี่ยนเอกสารเท่านั้นจึงไม่รัน lint/typecheck ซ้ำจากรอบก่อนที่ผ่านแล้ว
