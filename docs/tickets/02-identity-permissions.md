## Acceptance criteria

- [ ] ยืนยันวิธีเชื่อมบัญชีคณะและตัวระบุบุคลากร/หน่วยงานจากเอกสารหรือการทดสอบที่ได้รับอนุญาต ไม่เก็บรหัสผ่านขึ้นเองโดยสมมติ
- [x] ยืนยันบทบาทและตารางสิทธิ์เจ้าของ ผู้อื่นใน/นอกหน่วยงาน และสิทธิ์พิเศษถ้ามี
- [x] ครอบคลุมความลับ การเผยแพร่ รายการ/จำนวนผลค้นหา รายละเอียด ดาวน์โหลด แก้ไข และอ่าน audit
- [x] มีกรณีอนุญาตและปฏิเสธสำหรับทุกสิทธิ์ พร้อมหลักฐานเจ้าของระบบยืนยัน

## หลักฐานและขอบเขตที่ยืนยันแล้ว

### แนวทางล่าสุดที่ผู้ใช้ยืนยัน 12 พฤศจิกายน 2026

- ผู้ใช้ระบุว่า “อยากให้ระบบส่วนใหญ่อ้างอิงจากระบบเดิม แค่จะเปลี่ยน ui” และตอบ “ยืนยัน” ต่อแนวทางยึดระบบเดิมทั้งขั้นตอน วิธีล็อกอิน และสิทธิ์ โดยไม่เพิ่ม SSO หรือเปลี่ยนกติกาเอง
- T02 จึงตรวจเส้นทางล็อกอินเดิม การจับคู่ `STAFF_ID`/`DEPT_ID` และ `userlevel`/`userbook` เป็นฐานก่อน คำแนะนำให้ตรวจ OIDC ก่อนในบันทึกก่อนหน้าถูกแทนที่ด้วยแนวทางนี้ ไม่ใช่ข้อกำหนดงานปัจจุบัน
- คงตารางอ่านและสิทธิ์เจ้าของที่ผู้ใช้ยืนยันแล้ว หากโค้ดเดิมต่างให้บันทึกเป็นความต่าง ไม่ย้อนคำยืนยันหรือขยายสิทธิ์โดยเงียบ ๆ
- ต้องแก้ช่องโหว่และความเสี่ยงเลขซ้ำพร้อมรักษาพฤติกรรมการใช้งานเดิม ไม่คัดลอกวิธีตรวจรหัสผ่านหรือ role ที่ไม่ปลอดภัยเพียงเพราะมีในโค้ดเก่า
- ขั้นถัดไป: ตรวจการจัดการสิทธิ์เดิมและกรณีย้ายหน่วยงาน/ถอนสิทธิ์จาก source แบบอ่านอย่างเดียว พร้อมเทียบกับตารางที่รับรองไว้ แล้วระบุเฉพาะจุดที่หลักฐานไม่พอ การเชื่อมจริงยังต้องตรวจช่องทางที่อนุญาตและทดสอบในสภาพแวดล้อมที่ได้รับอนุญาต
- คำยืนยันนี้เป็นทิศทางการพัฒนา ไม่ใช่ผล integration; ตอนบันทึกยืนยันมีเกณฑ์ผ่าน 1/5 ต่อมาระบุแผนทดสอบ/รายงาน blocker ครบ AC5 จึงเป็น 2/5 และ T04 ยังรอหลักฐาน T02

## ตารางสิทธิ์ — ยืนยันอ่าน/แก้ไข มอบถอนสิทธิ์ และวงจรบุคลากรแล้ว 12 พฤศจิกายน 2026

T03 รอบสามรับรองรายละเอียดฟิลด์แก้ไข/version/audit และ PDF ครบแล้ว: owner แก้เฉพาะเรื่อง ผู้รับ หน่วยงานรับเรื่อง ผู้ลงนาม ความลับ เผยแพร่ PDF ไม่เปลี่ยนเจ้าของ/ชุด/ปี/เลขหลักย่อย/วันที่หนังสือ/เวลาออกจริง; ลับ→ไม่ลับโดยไม่มี PDF เป็นค้างไฟล์และบล็อกคำขอเลขถัดไปของผู้ทำรายการ ไม่เพิ่มสิทธิ์อ่านหรือแก้แทนตามตารางนี้

หลักฐานคำยืนยัน: รอบแรกผู้ใช้รับรองตารางอ่าน/สิทธิ์เจ้าของ ต่อมารับรองขอบเขตมอบถอนสิทธิ์และกฎย้ายหน่วยงาน/พ้นสภาพด้วยคำตอบ “ยืนยันตามนี้” ทั้งสองข้อ ส่วน contract identity, session timeout/ความสดข้อมูลภายนอก และกรณีพิเศษของ T03/T10/T11 ยังไม่ถือว่าได้รับอนุมัติจากคำตอบนี้

### ผู้ใช้งานและการระบุเจ้าของ

- เจ้าของ: บุคลากรที่เป็นผู้ขอเลขของหนังสือ ไม่ใช่ผู้ลงนามหรือผู้รับหนังสือ
- บุคลากรอื่นในหน่วยงานเดียวกัน/ต่างหน่วยงาน: เทียบหน่วยงานจากข้อมูลที่ server ตรวจสอบกับแหล่งบัญชีที่เชื่อถือได้ ห้ามรับหน่วยงานหรือสิทธิ์จาก form/header ที่ผู้ใช้กำหนดเอง
- ผู้ดูแลข้อมูลอ้างอิง: จัดการหน่วยงาน ประเภท และชุดเลขตาม T01 แยกจากสิทธิ์อ่านเนื้อหา แก้ไขแทน อ่าน audit และจัดการสิทธิ์
- การเงิน/พัสดุ: ข้อยกเว้นเวลาเดิม ไม่ได้ทำให้เข้าถึงหนังสือของผู้อื่นเพิ่ม
- บุคคลนอกคณะ/ยังไม่เข้าสู่ระบบ/บัญชีถูกระงับ: ไม่เข้าถึงงานหนังสือในระบบรุ่นแรก
- คงเจ้าของและหน่วยงานเดิมกับหนังสือ ใช้หน่วยงานปัจจุบันที่ตรวจสอบแล้วของผู้อ่านตัดสินสิทธิ์; ผู้ย้ายหน่วยงานยังเข้าถึงหนังสือของตนเมื่อยังเป็นบุคลากรคณะ แต่ไม่ใช้สิทธิ์เพื่อนร่วมหน่วยงานเดิม; สิทธิ์ชุดเลขให้ผู้ดูแลทบทวน ไม่ย้ายตามอัตโนมัติ
- เมื่อระบบรับรู้ว่าพ้นสภาพให้ปิด session และการเข้าใช้ โดยเก็บประวัติและเจ้าของเดิม ไม่โอนหรือลบอัตโนมัติ; วิธี/ระยะเวลารับรู้สถานะจากต้นทางยังต้องตรวจ integration
- ยังต้องยืนยัน stable ID และการจับคู่บัญชีเดิม ห้ามใช้ชื่อแสดงผลเป็นคีย์เจ้าของ

### กรณีตรวจรับ (Given/When/Then) — ผลคาดหวังด้านสิทธิ์ตามคำยืนยัน

ใช้บุคลากรจำลอง A (เจ้าของ หน่วยงาน X), B (หน่วยงาน X), C (หน่วยงาน Y), D (ผู้ดูแลหน่วยงาน Y) และ E (นอกคณะ) ไม่มีข้อมูลจริง กฎธุรกิจรองรับกรณีด้านล่างได้รับคำยืนยันสะสมทั้งสองรอบแล้ว เป็นผลคาดหวังสำหรับทดสอบ ไม่ใช่การรัน runtime สำเร็จ; รายละเอียด response/timeout/ความสดของ identity ต้องตรวจใน AC1/T04

| P14 B เป็น manager ชุด A แต่ไม่ใช่ชุด B | มอบ/ถอนผู้ใช้เลขใน A แล้วปลอม payload เป็นชุด B | A ผ่านพร้อม audit; B ถูกปฏิเสธ ไม่มี mapping เปลี่ยน |
| P15 A ถูกถอน grant ชุดหนึ่งโดยผู้มีอำนาจ | ขอเลขในชุดนั้นด้วย session เดิม | ปฏิเสธและไม่จัดสรรเลข แม้ login ยังไม่หมดอายุ; ชุดอื่นที่ยังมี grant และผ่านเงื่อนไขยังใช้ได้ |
| P16 D ถอน manager คนสุดท้ายของชุดหนึ่ง | บันทึกแล้ว manager เดิมพยายามมอบ grant อีก | ถอนสำเร็จพร้อม audit ไม่คง mapping เงียบ ๆ; manager เดิมถูกปฏิเสธ ผู้ดูแลระบบยังมอบ manager ใหม่ได้ |
| P17 manager มอบสิทธิ์ใช้เลขข้ามหน่วยงานภายในชุดที่ตนดูแล | ผู้รับ grant ขอเลข แล้วพยายามอ่านลับ/แก้แทน | ขอเลขผ่านเมื่อเงื่อนไขครบ; grant ไม่เพิ่มสิทธิ์อ่านลับหรือแก้แทน และมี audit การเปลี่ยน grant |
| P18 เจ้าของระบบอนุมัติการแต่งตั้งผู้ดูแล | ทำกระบวนการแต่งตั้งที่ server ตรวจสิทธิ์ แล้วผู้ใช้ทั่วไปพยายามตั้งตนเอง | ผ่านได้เฉพาะกระบวนการที่ได้รับอนุมัติและมี audit; การตั้งตนเองถูกปฏิเสธ |

P09 กรณี provider ล้มเหลวหมายถึงการเข้าสู่ระบบใหม่หรือคำขอที่จำเป็นต้องตรวจสอบ identity ใหม่และตรวจไม่สำเร็จ ไม่กำหนดให้ติดต่อ provider ทุก request เมื่อระบบรับรู้พ้นสภาพต้องปิด session ตามคำยืนยันแล้ว ส่วนระยะเวลา session ความสดสถานะจากต้นทาง และการใช้งาน session เดิมระหว่าง provider ล่มต้องตรวจ contract ใน AC1/T04 ไม่อ้างว่าผู้ใช้อนุมัติเลข timeout ที่เสนอไว้ก่อนหน้า

P01–P03 ต้องรันแยกทั้งรายการ/ยอด/รายละเอียด/PDF ไม่ใช่ทดสอบเพียงหน้าเดียว; P04–P08 ต้องรันทั้ง UI และคำขอฝั่ง server โดยตรง ขอบเขตของคำขอซ้ำ/concurrency และ rollback อยู่ในงาน implementation ที่เกี่ยวข้อง ขณะนี้ sandbox มี runtime เฉพาะ login/mapping แบบข้อมูลสังเคราะห์ ไม่ถือว่ากรณีสิทธิ์หนังสือ P01–P18 ผ่านทั้งหมดแล้ว

## แผนเชื่อม identity และหลักฐานที่ต้องได้

1. ระบุผู้ดูแลบริการบัญชีและเอกสาร integration ที่คณะอนุญาต: protocol, endpoint, transport, วิธีตรวจคำตอบ, logout/session/revocation และข้อจำกัดการทดสอบ ไม่สรุปว่าใช้ OIDC/SAML/LDAP จากชื่อ Intranet Account
2. ระบุข้อมูลที่เชื่อถือได้: ID ถาวรของบุคลากร, ID หน่วยงาน, สถานะบุคลากรภายในคณะ/บัญชีใช้งานได้, username และวิธีจับคู่ผู้ขอเลขเดิม รวมการเปลี่ยน username ย้ายหน่วยงาน หลายสังกัด และบัญชีพ้นสภาพ ไม่ใช้ email/ชื่อแทน stable ID โดยสมมติ
3. แยก authentication ออกจากสิทธิ์ชุดเลข/ผู้ดูแล และกำหนดผู้มีอำนาจมอบถอนสิทธิ์ ห้ามนำฟิลด์จาก browser หรือ role ที่ไม่มีคำอธิบายมาเป็น grant
4. ทดสอบในสภาพแวดล้อมที่เจ้าของอนุญาตด้วยบัญชีทดสอบ: สำเร็จ, รหัสผิด, บัญชีระงับ/นอกคณะ, ขาด ID/หน่วยงาน, เปลี่ยนสังกัด, หมดอายุ/ถอน session, provider timeout และ logout ไม่บันทึกรหัสผ่าน token cookie หรือข้อมูลส่วนบุคคลจริงลง repo/log
5. เก็บผลเป็นวันทดสอบ สภาพแวดล้อม รุ่น/config ของ integration ข้อมูลอ้างอิงแบบไม่ระบุตัวบุคคล ผลคาดหวัง/จริง และผู้รับรอง หากมีเพียง static source ให้ระบุเช่นนั้น ห้ามนับเป็นการล็อกอินสำเร็จ

### identity สำหรับการทดสอบ — ขอบเขตที่ระบุครบใน T02; implementation อยู่ใน T04

ใช้แผนทดสอบที่ระบุใน [รายงานตรวจเดิม](../specs/legacy-identity-permissions-analysis.md) เป็นข้อกำหนดส่งต่อ ไม่เพิ่ม test login ใน production AC5 ผ่านด้านการระบุวิธีและ blocker; ต่อมามี sandbox runtime tests 12 กลุ่มผ่านเฉพาะ compatibility login/mapping การตรวจสิทธิ์หนังสือ/production artifact ยังเป็นงาน implementation ที่เกี่ยวข้อง

- ใช้ข้อมูลบุคลากรสังเคราะห์ A–E ใน unit/integration tests โดยแทนตัวเชื่อม identity ภายใน test harness เท่านั้น ไม่เพิ่ม route เข้าสู่ระบบปลอมในแอปที่ส่งขึ้น production
- สำหรับ E2E ใช้บริการทดสอบของคณะและบัญชีที่ได้รับอนุญาต หากไม่มีให้ทดสอบกับตัวจำลองในกระบวนการทดสอบแยกที่ไม่รวมใน production artifact พร้อมรายงานว่าไม่ได้พิสูจน์การเชื่อมคณะจริง
- production ต้องปฏิเสธ header/query/cookie ที่ปลอม user/role/dept ไม่มี master password และไม่มี fallback เมื่อ provider ใช้ไม่ได้; build/deployment ต้องตรวจว่าไม่รวมตัวจำลองหรือ config ที่เปิด bypass
- ตรวจรับเชิงลบ: ส่ง identity ปลอมไปยัง production build ที่รันแบบ local ต้องเข้าไม่ได้; ตั้งค่า test adapter ใน production ต้องหยุดเริ่มระบบหรือ build ไม่ผ่านตามวิธีที่เลือกใน T04; provider ล่มต้องไม่สร้าง session

## ส่งต่อและข้อจำกัด

### บันทึกคำแนะนำก่อนยืนยันแนวทางยึดระบบเดิม — ไม่ใช่ข้อกำหนดที่อนุมัติ

บันทึกเพื่ออ้างอิงเท่านั้น แนวทางล่าสุดด้านบนมีผลแทนลำดับทางเลือก OIDC-first ในข้อ 1 ส่วนข้อเสนอด้าน grants/ย้ายหน่วยงาน/session ต้องตรวจพฤติกรรมเดิมก่อน ไม่ถือว่าผู้ใช้อนุมัติรายละเอียดทั้งหมดจากคำว่า “ยืนยัน” ทิศทางปรับ UI

อัปเดตภายหลัง: ผู้ใช้ยืนยันขอบเขต grants/ย้ายหน่วยงาน/พ้นสภาพตาม A3/A4 โดยตรงแล้ว ให้ยึดตารางปัจจุบันและ P12–P18 แทนสถานะ “ยังรอ” ในบันทึกเก่านี้ ค่า timeout และรายละเอียด provider ยังไม่ถือว่ายืนยัน

1. **ช่องทางบัญชี:** ขอผู้ดูแล IT คณะตรวจว่ามี SSO ที่รองรับ OpenID Connect (OIDC) สำหรับแอปนี้หรือไม่ ถ้ามีให้เลือกช่องทางนั้นก่อน เพราะแอปสามารถใช้ผลยืนยันตัวตนจากผู้ให้บริการได้ โดยไม่ต้องรับรหัสผ่านคณะเอง หากไม่มี ให้ใช้บริการยืนยันตัวตนที่คณะรองรับจริง เช่น SOAP เดิม เฉพาะหลังยืนยัน contract/TLS และทดสอบที่ได้รับอนุญาต ไม่เปิดหลายช่องทาง fallback อัตโนมัติ และไม่เลือกการ query ตาราง `PASSWORD` ตามโค้ดเดิมโดยลำพัง นี่เป็นลำดับทางเลือกที่เสนอ ไม่ใช่หลักฐานว่าคณะมี OIDC หรือ SOAP พร้อมใช้
2. **ตัวระบุบุคลากร:** ให้บริการบัญชีรับรอง ID ถาวรและหน่วยงาน หากใช้ OIDC ให้จับคู่บัญชีด้วยคู่ `iss` + `sub` แล้วเชื่อมกับรหัสบุคลากรที่คณะรับรองสำหรับประวัติเดิม ไม่สมมติว่า `sub` เท่ากับ `STAFF_ID` หรือมี department claim เสมอ ไม่ใช้ชื่อ/email เป็นคีย์เจ้าของ
3. **ผู้มอบถอนสิทธิ์:** เสนอให้ผู้ดูแลระบบที่เจ้าของแต่งตั้งมอบถอนสิทธิ์ชุดเลข โดยเก็บผู้กระทำ เหตุผล ก่อน/หลัง และเวลาใน audit การเพิ่ม/ถอนผู้ดูแลให้เจ้าของระบบหรือผู้ที่แต่งตั้งอย่างชัดเจนอนุมัติ ไม่เปิดให้บัญชีทั่วไปตั้งตนเป็นผู้ดูแล ขอบเขตนี้ไม่เพิ่มสิทธิ์อ่านลับหรือแก้แทน
4. **ย้ายหน่วยงาน:** เสนอคงเจ้าของหนังสือด้วย ID ถาวร และเก็บหน่วยงานเจ้าของเรื่องขณะออกเลขไว้กับหนังสือ ใช้หน่วยงานปัจจุบันที่ตรวจสอบแล้วของผู้อ่านเทียบกับหน่วยงานของหนังสือ เจ้าของเดิมยังอ่าน/แก้ของตนได้เมื่อยังเป็นบุคลากรในคณะ ผู้ย้ายออกหมดสิทธิ์แบบเพื่อนร่วมหน่วยงานเดิม แต่ยังได้สิทธิ์เจ้าของ/หนังสือเผยแพร่ ไม่ย้ายเอกสารหรือ grants ชุดเลขตามบุคคลโดยอัตโนมัติ ต้องให้ผู้ดูแลทบทวน grants
5. **พ้นสภาพ/ถอนสิทธิ์:** เสนอปิดการเข้าใช้ทันทีเมื่อระบบได้รับสถานะพ้นสภาพหรือคำสั่งระงับ ยกเลิก session ที่เกี่ยวข้อง และคงประวัติผู้ขอ/เลข/audit ไม่ลบหรือโอนเจ้าของอัตโนมัติ ตรวจ grants ปัจจุบันฝั่ง server ทุก operation สำหรับแหล่งบัญชีภายนอกต้องตกลงช่องทางและระยะเวลารับรู้การเปลี่ยนสถานะก่อนอ้างว่าปิดได้ทันทีที่ข้อมูลต้นทางเปลี่ยน
6. **session/บริการล่ม:** เสนอเริ่มจากหมดอายุเมื่อไม่ใช้งาน 30 นาที และอายุรวม 8 ชั่วโมง บังคับฝั่ง server โดยค่าตัวเลขเป็นข้อเสนอเฉพาะโครงการ ไม่ใช่ค่าบังคับจากมาตรฐาน เมื่อบริการบัญชีล่มไม่ให้ล็อกอินใหม่หรือยืดอายุยืนยันตัวตน; session เดิมใช้งานต่อได้เฉพาะขณะสถานะที่ตรวจไว้ยังสดตามช่วงที่ตกลง และยังตรวจ grants ในแอปได้ หากความสดหมดให้ปฏิเสธจนตรวจใหม่สำเร็จ ระยะเวลาความสดต้องตกลงกับคณะโดยไม่เกินความล่าช้าการถอนสิทธิ์ที่ยอมรับได้
7. **ทดสอบ:** ขอ test client/sandbox และบัญชีสังเคราะห์สำหรับเจ้าของ คนใน/ต่างหน่วยงาน ผู้ดูแล และบัญชีระงับ ถ้ายังไม่มี ใช้ test harness แยกตามแผนข้างต้นเพื่อทำงานที่ไม่ขึ้นกับ provider ต่อได้ แต่ T02/T04 ยังไม่ผ่านการเชื่อมต่อจริง

ตัวอย่างผลที่รับรองตาม A4/P12 แล้ว: A ออกหนังสือไม่ลับ/ไม่เผยแพร่ขณะอยู่ X แล้วย้ายไป Y หนังสือยังสังกัด X; A อ่าน/แก้ได้ในฐานะเจ้าของ, บุคลากรปัจจุบันของ X อ่านได้, บุคลากร Y คนอื่นอ่านไม่ได้ เมื่อระบบรับรู้ว่า A พ้นคณะ A เข้าไม่ได้แต่ประวัติยังอยู่

แหล่งประกอบคำแนะนำที่ตรวจเมื่อ 12 พฤศจิกายน 2026:

- [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html): กลไกยืนยันตัวตนและคู่ issuer/subject สำหรับระบุตัวตน ข้อมูลหน่วยงานและ mapping legacy ต้องตกลงเพิ่มเติม
- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): ปฏิเสธโดยปริยายและตรวจสิทธิ์ทุกคำขอ ไม่ได้กำหนดนโยบายย้ายหน่วยงานให้โครงการนี้
- [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html): จัดการ session/timeout ฝั่ง server และจัดการ session เมื่อสิทธิ์เปลี่ยน ตัวเลข timeout และการใช้งานช่วง provider ล่มด้านบนเป็นข้อเสนอของโครงการ

- T04 รุ่น local เริ่มจากกฎ T02 ที่ยืนยันแล้วได้ตามคำยืนยันล่าสุด; production ยังรอ T13 ห้ามเลือก protocol สร้างฐานรหัสผ่านคณะเอง หรือเปิด test login ใน production เพื่อเลี่ยงเงื่อนไขก่อนเปิดใช้
- T06/T07/T08/T09 ใช้ตารางที่รับรองแล้วเป็นกฎเดียวกันฝั่ง server ครอบคลุม URL ตรง ไฟล์ จำนวนผล และ audit; T03/T10/T11 ยืนยันสิทธิ์กรณีพิเศษต่อ
- รอบเอกสารก่อนเตรียม sandbox ไม่เปลี่ยนโค้ดแอป dependency ฐานข้อมูล หรือระบบเดิม; รอบ sandbox ต่อมาสร้างฐานสังเคราะห์แยกและทดสอบ login ตามบันทึกด้านบน ไม่อ้างว่าผ่าน faculty integration หรือ concurrency
- ผลตรวจ 12 พฤศจิกายน 2026: `npm.cmd run lint` และ `npx.cmd tsc --noEmit` ผ่าน; ลิงก์ local ใน T02/README และยอดสถานะผ่าน; QA ตรวจร่างแบบ static ไม่พบ Critical/High/Medium มีข้อเสนอให้แยกกรณี provider ล่มออกจาก session เดิม ซึ่งเพิ่มคำอธิบายไว้แล้ว ผลนี้เป็นการตรวจร่าง ไม่ใช่การรับรองเกณฑ์ T02 หรือผล runtime
- QA รอบบันทึกคำยืนยัน: ไม่พบ Critical/High/Medium; พบข้อความสถานะเก่าในสเปกและหัวตาราง/V1 ระดับ Low ซึ่งแก้ให้ตรงคำยืนยันแล้ว รอบนี้เปลี่ยนเอกสารเท่านั้นจึงใช้ผล lint/typecheck รอบก่อน ไม่รันซ้ำ และยังไม่อ้างว่าผ่าน integration
